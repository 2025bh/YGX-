# 忆古轩项目交付系统后续架构与改造建议

评估日期：2026-09-24  
复核日期：2026-09-25。报告记录改造前结论；后续实施结果以项目交付窗口记录和任务账本为准。  
评估性质：实际代码审查、业务基线对照、已有测试证据复核；不是重构开工单。  
范围：WorkBuddy 原系统、system-v22 隔离修正版、NocoBase Community 业务 POC。  
本轮边界：未修改上述系统代码，未迁移数据库，未删除文件，未安装框架，未重启服务，未操作飞书生产环境。

## 一、先说结论

**我最推荐方案 B：保留现有产品，分步整理业务核心，适度配置化。现在不迁移到 NocoBase，也不整体重写前端。**

现有系统并不是没有基础。它已有项目、设计、生产、批次、出货、安装、售后、员工权限、附加字段和手机界面；`spec.js` 已经承担一部分统一流程与字段定义。9 月 23 日的隔离修正版，又补上了节点查看、重复退回、资料保留、最终报价权限、多人生产负责人、生产日期留空和外购并行等重要成果。**这些应该接续，不应该推倒。**

真正的问题是：系统已从演示工具长成了多岗位业务系统，但保存机制、权限入口、状态变更和自动联动仍以演示程序的方式组织。新增一个需求，经常要同时修改字段定义、界面、多个接口、权限判断及通知分支。换一个框架不会自动消除这种重复。

### 1.1 最重要的判断

| 判断 | 本项目的实际依据 | 建议 |
| --- | --- | --- |
| 业务成果值得保留 | 五类路径、已有表单组件、人员组、批次有效性、隔离版退回与附件历史已经存在 | 原系统保留；隔离修正按功能合入，不能整目录覆盖 |
| 最大风险不在 UI | 原系统附件下载缺记录权限；整库 JSON 直接覆盖；损坏时自动重建演示库；审批仍为桩实现 | 先补数据与权限底线，再谈大规模美化 |
| 自建字段不用从零做低代码 | 已有 `field_defs`、`custom` 和字段设置页，但保存、必填和节点归属没有完整贯通 | 统一内置字段与附加字段的运行机制，保留轻量设置页 |
| 流程不能只靠数组位置 | 中文节点名同时当标识；推进、退回、外购、批次、审批分别写条件 | 引入稳定节点 ID、流程版本和少量明确的业务命令，不造通用工作流平台 |
| NocoBase 有局部价值，迁移收益未成立 | 数据表、普通权限和 API 可用；员工页、关键校验、私有文件仍需另写代码 | 保留 POC 证据，不作为当前主线 |
| 目前不能认定任何一版已满足正式上线 | 真飞书审批/登录未完成；完整异常账本、多批合并出货、真实员工与实体手机验收不完整 | 明确区分试用通过与上线通过 |

**一句话：保留员工已经能用的部分，把“如何保存、谁能操作、如何流转、怎样联动”整理成少数稳定模块，再补业务缺口。**

## 四、必须先处理的问题

优先级：P0 为接入真实敏感资料或正式多人使用前的阻断项；P1 为会造成流程、权限或数据含义错误的高优先级；P2 为维护及体验改进。下述风险不等于已经发生真实泄漏或数据损坏。

### F01 / P0：保存失败可能影响整库，损坏后不应自动造新库

**证据：**[O server.js:155]([原本机路径，公开版以本工程为准] 加载/保存实现位于 `server.js:160`。两版行为需分开判断。

两版 `saveDB()` 都直接用 `writeFileSync` 覆盖整份 JSON。O 读 JSON 失败后尝试备份，备份错误被忽略，然后走 `seed()` 与 `saveDB()`，可能用演示数据替代原业务库并继续运行。S 已在 JSON 解析失败时停止启动，应保留该保护；但没有验证解析后的整体结构，合法 JSON 的 `null/false/0` 仍会落到演示初始化分支，缺字段的对象可能在迁移中报错。启动迁移还会自动改旧状态、补日期。

单 Node 进程的同步写并不等于每次点击必然互相覆盖，但它没有多实体事务、持久化提交边界和跨进程保护。整库写入也会随记录增长阻塞请求。

**必须改：**已存在库损坏时停止业务写入并报警，不自动重建；备份需验证可恢复；迁移从启动隐式动作改为有版本、有预检、有结果核对的显式步骤。过渡期可做原子替换和写入串行化，但不能将其包装成长期交易数据库。

### F02 / P0：原系统附件权限只到“已登录”，没有到项目与字段

**证据：**[O server.js:1105]([原本机路径，公开版以本工程为准] 上传与 `1115` 下载。文件元信息没有所属项目、节点及敏感级别；下载路由找到 ID 就返回内容。

因此“页面不显示最终报价”不能保护已知地址的文件。另有客户端提交的 MIME 被用于同源 `inline` 输出，缺少对主动内容类型的限制，正式上线前应检查 HTML/SVG 等类型的执行风险。

S 的 `canSeeFinalQuotation`、响应脱敏和下载检查已经改善，但下载要递归搜索项目资料与历史引用；附加报价字段还用 `label === '最终报价表'` 识别。改标题不应改变保密级别。

**必须改：**保留 S 的业务限制，用稳定字段 ID 和明确文件归属执行服务端权限；上传、预览、下载、历史、导出同一口径。文件引用至少记录 `project/task/node/field/version`，敏感性不从中文标题猜。历史资料缺归属时默认拒绝或待管理员核对，不能直接全部放开。

### F03 / P0：演示身份和配置不能直接拿来上线

**证据：**O `server.js:29`、S `:33` 使用直接 SHA256；种子数据提供统一试用密码。会话保存在本地数据中；管理员初始化数据包含系统配置。`feishu.js` 的 OAuth 换取身份仍是待实现分支。

已有停用与重置密码清理会话的保护应保留。但“有登录页”不等于已经具备正式身份、安全会话与密钥隔离。

**必须改：**正式飞书身份绑定不可仅按姓名；采用稳定员工标识，核验在职和权限。正式密钥只在服务端保存，管理页面显示脱敏值；HTTPS、安全 Cookie、会话有效期、登录限流和上传约束补齐。本地账号若保留，需专用密码哈希和独立试用边界。不要为 POC 立即采购部署，但不能直接对公网开放当前演示服务。

### F04 / P1：附加字段“看得到”不等于“能可靠提交”

**证据：**O `server.js:646`、S `:763` 定义 `needCustom()`，两份源码中该调用名都只出现一次，即定义本身。O `mergeCustom()` 主要用于项目创建和独立字段保存；设计推进页面却会发送 `data.custom`，推进接口未合并这些值。

结果是原系统部分节点附加字段可能随“提交下一节点”丢失；S 已补主要合并路径，但服务端“附加字段必填”的闭环仍缺。浏览器必填检查不能代替接口校验。

另外，当前附加类型只覆盖文本、日期、数字、金额、下拉、文件等，缺人员/人员多选等统一支持；作用域未完整覆盖批次与出货。

**必须改：**一个字段定义统一驱动显示、草稿、校验、保存、详情和历史。不是再写一个表单渲染器，而是合并内置与附加两条运行路径。增加节点字段时必须有“填值→保存→推进→刷新→退回→再查看”回归。

### F05 / P1：权限规则分散，而且组顺序会改变数据范围

**证据：**O `server.js:170` 的 `permsFromRoles` 仅保存一个 `scope`，多个非 self 组按遍历覆盖；[O server.js:883]([原本机路径，公开版以本工程为准] 附近另有设计、生产、安装授权；前端 `01-core.js:188` 再实现一遍。

本轮只读函数复现：`assigned→prod` 与 `prod→assigned` 得到不同最终范围。页面和动作使用集合合并，数据范围却不是。原 `prodAllowed()` 仅看管理员或 `prod` 能力，不能落实木工、油漆、采购、发货各节点差异。

S 已加强演示外接负责人和分段生产权限，但服务端 `prodAllowed` 与前端 `canOperateNode` 仍不一致；前端可能显示可操作，提交时服务端才拒绝。附加字段独立保存又有另一套授权，可能绕开“只编辑本节点字段”的预期。

**必须改：**统一策略模块分别回答项目可见、字段可见、节点可编辑、可退回、可补正五个问题。保留可配置组和岗位能力；服务端给前端返回允许动作及拒绝原因，前端不再推导一套权威权限。多岗位按明确可见集合合并，禁止依赖数组顺序。

### F06 / P1：字段校验和变更提交不是完整原子动作

**证据：**O `server.js:686` 的 `needNode()` 只判断字符串非空，`false` 变成字符串仍非空。本轮内存复现确认必填核对框传 `false` 被接受，S 对这一点已拒绝。

S `applyNodeFields()` 增加了类型、选项和人员检查，值得保留；但批次、出货、售后、附加字段仍有独立赋值分支。字段定义修改接口还会先改部分属性，再校验后续属性；后续失败时内存对象可能已变化，下一次保存可能把它落盘。

**必须改：**先在副本上归一化、校验和授权，全部通过后再统一提交；失败不得留下局部数据变更。标准化 PATCH 语义：“没传”保留，“明确清空”在允许时清空，“替换附件”保留历史。S 为避免退回丢值而跳过空值是有价值的保护，但不是长期完整的清空协议。

### F07 / P1：节点名称和顺序承担了过多含义

**证据：**O/S `spec.js` 用中文名作为节点键；各接口依赖 `indexOf(status)` 推算下一步；前端详情、通知、校验、迁移也判断相同中文文本。

改“复尺确认”的显示名称，不应同时影响旧记录、退回目标、权限和统计。插一个节点也不应改变在途任务含义。

**必须改：**稳定 `node_id` 与中文 `label` 分离；任务记录 `flow_version`；保留旧中文状态映射。新增版本默认用于新项目，在途项目是否升级需明确，不自动按新数组重算旧任务。

**暂时不要做：**允许管理员任意拖动线上流程后立即影响所有项目。可视化流程编排不是当前必要前提。

### F08 / P1：退回已取得进展，但还不是独立、统一的业务能力

**证据：**[S server.js:1237]([原本机路径，公开版以本工程为准] 通用保存/退回/恢复/推进分支；`rollbackIssue`、`markRollbackProgress`；批次另有资料补正接口。

保留项：重复退回、原因、前态快照、`rollback_recover_stage`、下游暂停、原字段和文件历史。问题在于这些逻辑与 HTTP 路由、数组位置、`paused_by` 单指针、批次分支交织；顶层字段与 `node_values` 又共同表达节点资料。

**必须改：**抽出明确的退回命令和依赖处理：核验目标→判断是否只能补正→保存前态→暂停受影响的未完成任务→保留已发生事实→重完时复用下游记录。管理员“任意次数退回”不等于抹掉已发货事实、跳到未来节点或无条件重开终止项目。

S 已存在“管理员带 reopen 标记重开完成项目”的代码，不能据此认定业务已批准全部重开规则。需要独立业务确认和用例，不直接迁入正式入口。

### F09 / P1：当前批次与审批关系不足以表示“多批一次出货”

**证据：**O `server.js:868`、[S server.js:1032]([原本机路径，公开版以本工程为准] 的 `newApproval()` 保存单个 `batch_id`；`approvalOfBatch()` 按单批查第一条记录。页面和接口也沿单批创建审批。

这能表示“一批一张”，不能完整表示用户确认的“一次出货覆盖多个完整生产批次”。“是否分批出货”布尔值不能代替关联关系。重新申请若只找到旧终止/驳回实例，也缺少清晰的申请轮次模型。

**必须改：**把生产批次、一次出货、审批轮次分开。一次出货关联多批；审批轮次关联该出货；一个批次此阶段仍整批发，不新增数量拆发、库存台账或成本系统。已完成出货覆盖哪些有效批次，应可直接查询而不是凭状态猜。

### F10 / P1：安装建档与派工已分离，但门禁尚未满足最新基线

**证据：**S `server.js:2001` 在实际发货时检查并创建安装；[workflow-control.js:26]([原本机路径，公开版以本工程为准] 的 `readyForInstallation()` 只检查批次建齐、有效批次已发货和批次异常标志，单批只看已出货。

本轮纯函数复现：全部有效批次已发货，即使生产任务标记异常、外购状态仍为未下单，函数仍返回 `true`。现有前置调用也没有补齐这些派工条件。**这不是实际派过错误工单的证明，但确实是规则缺口。**

另有每张审批的“是否分派安装”可直接覆盖项目级 `need_install`，后续批次选否可能与已建安装档案冲突。首批后才改成需要安装的补建，也应成为独立幂等命令，而不是等下一次发货。

**必须改：**项目级安装意向单独管理；安装按项目唯一；派工统一校验“批次确认建齐＋所有有效批次完成且已被实际出货覆盖＋必要外购满足＋无影响派工的阻断异常”。保留首批建档，不退回旧的全部出完才建档案。

### F11 / P1：并行外购只在部分路径完成，不能据单批通过覆盖多批

**证据：**S 的 `purchase-save/purchase-complete/purchase-correct` 将外购独立于主生产推进，是正确方向；`server.js:1307` 附近还明确拒绝 `t.batch_flow` 的补正，其他外购入口也有分批限制。

当前证据不足以证明多批项目的外购责任、满足条件与批次齐货已贯通。不能让“管理员任何情况下可补正外购”的业务承诺只在非分批时成立。

**必须改：**明确外购目前是项目/生产任务级并行事项，还是存在已确认的按批拆分需求。按当前基线先保留项目级，统一纳入出货和安装门禁；已审批或已发货只补正资料，不重写事实。不擅自设计采购 ERP。

### F12 / P1：异常还是单开关，并且覆盖项目阶段

**证据：**O `server.js:712`、`:732`；S `:872`、`:892` 和安装推进、异常接口。

现有 `is_exception/exception_desc` 可被“否”清除，项目 `project_status` 会变为“异常”；多个问题没有独立 ID、处理意见和逐条关闭记录。生产或安装负责人可解除的旧路径，也不满足“新异常默认阻塞，仅管理层可改非阻塞”的决定。

**必须改：**新增最小异常账本，阶段与风险分开。记录来源、影响范围、阻塞标志、意见、解决/关闭事实；旧单开关暂作兼容展示，不作为真相。不能从当前“异常”状态猜过去阶段后批量覆盖，历史不明确的项目列入待核实。

### F13 / P1：当前飞书是适配桩，不是已接通的业务系统

**证据：**[O feishu.js]([原本机路径，公开版以本工程为准] 的 `exchangeCode`、`createShipApproval`、`syncApproval`、`notifyShipGroup`；S 同类实现仍在。

- 未配置时返回 MOCK；配置齐全时创建函数仍返回空实例号，`mock:false`，没有实际创建请求。
- 查询审批返回空状态；群通知主要写本地日志；没有经验证的事件验签、去重和状态对账链路。
- 服务端先把本地审批推进，再调用该适配桩；不能只替换几行 HTTP 就认为接入完成。
- `feishu_sync` 是管理员传入状态，不等于真实飞书事件回调。
- 财务与条件确认在本地一次动作处理，不证明真实飞书会签/串签与授权正确。
- 未发现已实现的业务 Base 双向同步，也没有完整采购/木材下单原生审批链路；不能把预留权限标签当成功能完成。

**必须改：**演示与正式适配显式分开；正式提交失败时不得显示已发起。业务命令先形成待提交申请，再可靠发起、绑定实例、接收事件、校验版本与状态。回调重复或迟到不能放行已暂停任务。需要可重试待发送记录和已接收事件记录，不需要先上消息中间件。

历史愿景是“底层可放飞书”，实际当前代码以本地 JSON 为主。**飞书作审批协同，和飞书作全部业务主库，是两个不同决定。** 未确认前不要同时让两边可随意写同一业务事实，也不要宣称已完成飞书数据接入。

### F14 / P1：还有能直接导致错误的字段语义与更新口径

| 具体问题 | 位置 | 建议 |
| --- | --- | --- |
| 用材料到场日期校验“工厂最快发货时间” | O `server.js:1466`；S `:1948` 的 `fastestShip` 优先取 `material_arrival_date` | 使用明确的最早可出货业务字段，不能以材料日期替代；补早于工厂日期拒绝用例 |
| 人员存 ID、姓名、主负责人、多人名单并存 | 设计转接、生产任务、批次、售后派工；S `manager_id/manager_ids` | 多人 ID 列表是分配真相，主负责人仅作兼容投影；姓名只作历史显示，不用于权限身份 |
| 多处内置日期使用 UTC 截日期 | O/S `today()` 的 `toISOString().slice(0,10)` | 业务日期统一上海时区，操作时间保存带时区时间戳；不能把日期与时刻混用 |
| 日期默认规则在语音入口又出现一套 | S `server.js:2488` 默认抽取提示“没提到就用今天”，与同处“没提到不输出”也冲突 | 生产日期缺失继续留空；语音识别只是候选值，必须人工确认，不据提示自动落库 |
| 记录正文和节点快照存在多份同义值 | 顶层字段、`custom`、`node_values`、项目汇总字段 | 明确每个字段由谁维护，其他为只读投影或历史，不能多头可写 |

## 六、NocoBase POC 的真实价值

### 6.1 已证明和未证明

已证明：在隔离环境可以建表/字段、应用基础表和行权限、提供 API；独立员工页可以完成新建项目到转接生产；虚构重复转接返回 409；自写下载入口能区分销售与设计师；四个视口宽度可用。

未证明：完整五类业务、反复退回和事实保留、多批出货/安装、异常账本、飞书审批事件、断网恢复、实体手机、真实员工权限、长期升级和维护成本。

**POC 的员工页面是手写页面，不是后台加字段就自动更新的页面。** N `schema.mjs:24`、`server.mjs:23`、`public/app.js:7` 分别维护数据字段、节点字段及界面字段，反而再次出现三处定义。

### 6.2 逐项评估

| 维度 | 本次实际收益 | 新复杂度/未解决点 | 对当前系统的取舍 |
| --- | --- | --- | --- |
| 数据模型 | 关系数据库、建表接口、索引基础具备 | 初测“一对一”只生成普通索引；后补唯一约束不能证明多步业务事务完整 | 吸收显式关系、唯一约束思想，不必为此迁平台 |
| 字段管理 | 后台可以增加普通字段 | 不会自动出现在当前独立员工表单；仍要修改代码 | 对接统一字段目录的思想值得吸收，现系统已有入口更易延续 |
| 表单生成 | 原生有类型化配置基础 | 员工样板使用自写日期、人员、文件等组件，未证明原生表单满足需求 | 保留自己适合员工的表单，统一元数据即可 |
| 权限 | 原生表权限、创建人行过滤、禁读字段过滤有证据 | “当前负责销售/多人生产分配”不是创建人；网关主要使用管理员凭据另做业务校验 | 吸收服务端字段/行过滤；不采用“管理员代理自动等于安全”假设 |
| 工作流 | Community 触发器入口可见 | 没有实际跑完整原生工作流，不能说已经解决退回或幂等 | 当前用清晰命令与条件函数更直接 |
| 文件 | 上传关联能力存在 | 原生本地文件直链在本配置实测越权；POC 另建私有目录与 JSON 文件索引 | 私有下载入口思想保留，必须有独立归属与统一权限 |
| API | 普通 CRUD 方便 | 创建项目和任务为两次 HTTP；生产创建与节点推进也分开，不能自动获得一个事务 | 学习接口契约，不把业务动作拆成前端自由拼 CRUD |
| 手机端 | 自写员工页四宽度通过 | 这不是原生后台移动体验的证明；实体手机未验 | 继续共享现有业务规则，不为手机换后端 |
| UI 自由度 | 自写前端可自由设计，员工无需进后台 | 自由来自额外前端，平台并未消除这一维护层 | 现有前端也可做到，迁移无独有收益 |
| 自定义业务流程 | 编码后技术上可承载 | 关键流程仍在 Node 网关，另增平台数据结构、权限与升级约束 | 不把“能实现”当成“更省维护” |
| AI 后续修改成本 | 表元数据有助理解 | 现 POC 要理解平台、网关、前端、部署和多份字段表 | 吸收元数据和明确 API，避免多层重复真相 |
| 飞书集成 | 可通过自定义服务对接 | 本 POC 未完成飞书认证、审批、回调或通知 | 统一独立飞书适配器，未来换数据库也可复用 |
| 长期维护 | 成熟平台能提供一部分通用能力 | 本机增加 WSL/Docker/PostgreSQL/NocoBase/网关/文件目录；曾需恢复守护进程，长期升级未验 | 现阶段维护负担有增加，收益未覆盖成本 |

原生附件问题的限定：NocoBase 2.2.15、本次本地存储配置和虚构文件中，设计师附件记录 API 为 403，但已知原始下载链路返回了测试文件。不能推广为“NocoBase 所有配置都不安全”。官方当前[文件存储说明](https://docs.nocobase.com/file-manager/storage)也区分权限入口与原始存储链接，并提示无签名链接的存储风险；该资料用于解释风险，不替代本地版本验证，也不意味着只有付费才可能做安全文件方案。

### 6.3 更容易被忽略的成本

1. `server.mjs:176` 先建项目再建设计任务；`:251` 先建生产再更新设计。第二步失败需要补偿/重试设计，PostgreSQL 在底层并不会把两次独立 API 自动合成事务。
2. `locks = new Set()` 只防当前网关进程内冲突。重启、多实例和超时结果不明不由它解决。
3. 业务 POC 中人员 ID、JSON 多人列表和名字仍有多种表示；平台不自动使业务模型规范。
4. 文件二进制和本地 `index.json` 与平台数据库分开，新增备份一致性问题。
5. 当前旧版对照是静态截图，不是同一项目、同一岗位实操的耗时/错误率对比。因此尚无“员工更好用”的比较证据。

### 6.4 应吸收什么，不吸收什么

**吸收：**字段元数据、稳定关联、数据库唯一约束、服务端行/字段权限、清晰 API、普通设置与员工操作分离。

**自己实现更简单：**这五类固定路径、节点表单、项目负责人授权、最终报价规则、反复退回、外购并行、首批安装与齐货门禁。用少量测试充分的模块，比先映射成通用流程配置更直接。

**暂不吸收：**通用 Collection/Workflow 后台作为员工入口；管理员令牌包办全部业务而长期重复维护两套权限；为追求低代码给每个特例再套插件；只因 POC 已花时间就迁移。

结论仍是 **A 已部分成立：技术可实现；B 尚未成立：更稳定、更好维护且不增使用难度**。目前员工样板满足“不进原生后台”的局部要求，但如果后续日常业务仍需频繁进入原生后台修状态、补任务，应直接判为不符合使用要求。

保留 POC，不继续扩建。若未来重评，应限定为三个可验收问题：加普通字段能否自动到员工表单；关键回退/权限能否少写代码而不降低安全；升级与备份恢复能否比现方案更省事。未获用户选择前不开展这些试验。

## 七、配置化应该做到什么程度

**建议目标不是“所有东西都可配置”，而是“高频、低风险、业务人员看得懂的变动，不必改代码”。** 数据事实、授权边界和重要联动仍用明确代码保证。

### 7.1 配置边界

| 对象 | 建议程度 | 管理页面允许什么 | 不允许直接做什么 |
| --- | --- | --- | --- |
| 普通附加字段 | 优先配置化 | 新增、改标题/说明、排序、选择所属节点、停用展示 | 删除已有业务值；改稳定字段 ID |
| 字段类型 | 固定类型库＋配置选择 | 文本、长文本、日期、数字、金额、人员、多人、单选、多选、文件 | 把已有人员字段任意改成日期；新组件类型仍需开发和测试 |
| 必填 | 配置但有版本 | 设置普通字段提交时必填，简单条件必填 | 强制新必填导致已完成历史记录变非法；关闭正式审批必要核对 |
| 选项 | 优先配置化 | 新增选项、改显示名、排序、停用 | 删除已使用选项或复用旧 ID 表示不同含义 |
| 默认值 | 谨慎配置 | 普通文本默认值、明确的当前操作者引用 | 生产业务日期自动填今天；分批默认否；自动制造完成事实 |
| 字段保密 | 受保护策略引用 | 设置普通字段可见岗位；敏感字段沿已批准策略 | 改标题解除最终报价限制，或管理员在普通字段页随意下调保密 |
| 节点表单 | 中等配置化 | 同一个节点增删展示项、分组、说明、字段顺序 | 把后续事实字段挪到前序后允许提前填写生效 |
| 节点路径 | 先版本化，不开放自由编排 | 查看五类路径；新版本先预览、测试和审核 | 线上拖动顺序即重排所有在途项目 |
| 岗位与人员 | 优先配置化 | 人员入组、岗位能力、负责人选择、岗位默认人 | 业务代码继续按具体姓名判断权限 |
| 权限 | 参数可配，策略代码化 | 页面能力、可见集合、指定操作人；引用固定策略 | 任意表达式写访问控制；同一动作由前后端分别定义规则 |
| 通知 | 较适合配置 | 收件岗位/关系、模板、渠道、开关 | 通过配置跳过业务提交、伪造真实审批通过 |
| 自动化 | 小范围配置 | 已知事件挂通知；选择经过测试的固定动作与参数 | 任意脚本、任意跨表改写、无人审查即启用重要联动 |

内置字段和附加字段不必物理塞进同一张表，但**运行时必须合成为同一份有效字段目录**。内置定义提供受保护 ID、类型与业务约束；管理员配置提供允许覆盖的标题、说明、展示和普通附加项。不能用两条独立的保存与必填路径。

### 7.2 明确留在代码中的规则

- 能看项目不等于能改节点；最终报价只有本项目销售与管理员可见。
- 普通退回不可越过其他岗位已完成的交接；管理员反复退回保留事实与资料。
- 转接生产只能建立/复用对应生产任务，负责人继承完整多人列表。
- 首批实际发货建立唯一安装档案，齐货与阻断条件满足才可派工。
- 已发货批次仅资料补正，不撤销真实出货；一个生产批次整批发。
- 一次出货可覆盖多个生产批次，审批轮次保留；退回与迟到审批事件不能冲掉当前版本。
- 每条异常独立处理，只有授权管理人员可调整阻塞规则。
- 提交的事务、重复请求防重、事件去重、文件权限、备份恢复与迁移。

这些是公司的业务底线，不是让零基础管理员组合几十个条件块的题目。把它们写成命名清楚的函数、配真实场景测试，比做一个复杂规则编辑器更稳。

### 7.3 管理员日后实际能怎么改

例：在“上门量尺”增加一个“现场电梯是否可用”的普通单选字段。管理员在现有字段设置页选节点、选类型、填选项、决定必填、预览手机表单、发布配置即可。员工表单、保存、详情、草稿和历史自动使用该定义，不改多个页面。

但如果新增“吊装审批通过才允许发货”，这是新的业务联动，仍需要开发命令、权限和测试。**新增信息字段可以自助；新增业务后果需要受控开发。** 这一区分比承诺“以后任何改动都不用编码”可靠。

## 八、三套可选方案

以下均保留原系统与 POC，不做未经批准的数据或文件删除。开发量是本次静态审查后的粗估，按一名熟悉项目的工程师计；不是承诺工期，也不按 AI 生成代码速度折算。真实数据清理、飞书授权等待、业务验收和服务器准备另计。

### 方案 A：先保稳，继续沿用现有组织方式

针对 F01～F06 等风险和已确认业务偏差做补丁，按功能合入 S 修正；保留当前大文件、JSON 和接口。给关键权限、退回、字段、发货补测试，不引入完整新数据模型。

适合短期继续虚构数据试用、尽快修眼前问题。**它不是完整满足最新业务基线的方案**：多批一次出货、逐条异常和可靠原生审批仍要另做，所以后续会继续付维护成本。

### 方案 B：保留产品，分步整理业务核心【推荐】

保留现有页面、组件、业务类型和员工操作；吸收 S 的修正和测试。把权限、字段、流程命令、保存、文件和飞书适配整理成稳定模块。统一字段机制、逐步采用事务存储，新增最少的异常/出货/审批轮次关系；每次只替换一个业务能力，不一次换掉系统。

适合“已有大量业务成果、规则仍在完善、希望 AI 可持续开发”的现状。需要一定前期整理，但能把后续变更从“全系统搜字符串”变成“改一个明确模块并跑对应测试”。

### 方案 C：接口兼容的后端重建，逐步换底座

保留 UI 外观、需求与旧数据，重新实现认证、领域服务、关系数据库和 API；通过兼容层逐步把原页面接到新后端。NocoBase 不是默认选项，仍需独立选型。前端可待后端稳定后再局部整理。

适合已证明现有后端无法承受规模或维护需求的阶段。当前尚无负载、故障率、维护耗时证据支持立刻承担这一成本；会同时维护两套后端并复验大量已有规则。

### 8.1 横向比较

| 维度 | A：先保稳 | B：整理业务核心 | C：后端重建 |
| --- | --- | --- | --- |
| 保留什么 | 几乎全部代码和 UI | UI/组件/现有 API 兼容面/业务路径/有效测试；逐步保留可用实现 | UI、业务规范、历史数据、测试场景；旧后端作回退参考 |
| 修改什么 | 安全、字段保存、关键权限和当前 Bug | 单一字段目录、统一策略、业务命令、事务保存、异常与出货关系、集成边界 | 大部分服务端、存储、接口内部实现与部署方式 |
| 删除什么 | 本阶段不删 | 本阶段不删；将来重复实现退役需验证和批准，原快照保留 | 不删旧系统；切换后也先只读归档，另行批准才清理 |
| 数据结构 | 少量兼容字段，主要 JSON | 需要；新增关系和版本，先复制库演练、渐进映射 | 需要完整映射及迁移计划 |
| UI 是否改变 | 小修 | 主要操作习惯不变；表单统一、手机详情收敛 | 外观可暂不变，但兼容接口和权限状态需大量复验 |
| 对现有使用影响 | 单次小，后续频繁补丁 | 单次按功能隔离；有阶段性验收，数据切换要维护窗口 | 较大；双实现期间容易出现行为差异 |
| 初步开发量 | 约 8～15 人日，范围仅止血与必要合入 | 约 30～50 人日，分批交付；优先两阶段约 8～12 人日 | 约 60～100 人日或更多，重验成本较高 |
| 主要风险 | 技术债积累；补一个地方漏另一个 | 抽取时行为变化；数据兼容需要细致验证 | 重复实现遗漏业务、迁移出错、长期双系统漂移 |
| 回滚难度 | 代码较低；涉及数据修正仍不能随意回档 | 代码低至中；数据库切换中等，需变更日志与对账 | 高；新旧模型差异大、回切后数据对齐困难 |
| 后续维护成本 | 高 | 中等前期投入，长期较低且可控 | 初期很高，后期取决于是否真正统一规则 |
| AI 后续难度 | 仍要搜索大文件和重复条件 | 边界清楚、输入输出明确、有回归场景，最适合当前 | 新旧双栈阶段高；新系统稳定后可能降低 |
| 最大收益 | 最快改善当前试用 | 同时保护成果与降低后续改动成本 | 后端可以系统性消除历史结构约束 |
| 最大缺点 | 难满足长期维护及新业务关系 | 不像全新重做那样立刻“看起来全新” | 代价和不确定性明显超过目前已有证据支持 |

### 8.2 为什么推荐 B，而不是折中好听

1. **规格表和表单已存在。** 最短路径是补成统一机制，而不是迁平台后又造一份。
2. **最近的修正具有真实业务价值。** 节点查看、反复退回、报价权限和负责人继承已经付过验证成本，重写必须重新付一次。
3. **真正缺口集中。** 大部分风险集中在保存、授权、字段运行、退回、异常、出货和集成，尚无证据要求整个 UI 或全部框架换掉。
4. **数据关系确实需要局部调整。** A 的补丁不能把单个 `batch_id` 变成可靠多批一次出货，也不能让单异常开关成为逐条账本。
5. **B 可先交付小收益。** 字段不丢、权限一致、资料退回保留都能单独验收，不需要等新系统做完。
6. **对业务人员最友好。** 员工继续在“项目、当前事项、提交、查看、退回”中操作，不看到仓储层、工作流引擎或 NocoBase 概念。

## 九、推荐方案的具体结构

这不是要求创建十几个空目录，而是给当前大文件划清职责。优先提取实际有重复或有风险的代码；没有必要为每个函数新建抽象层。

### 9.1 从当前文件逐步提取

| 稳定职责 | 来源 | 整理后的唯一责任 |
| --- | --- | --- |
| 业务规格与字段目录 | `spec.js`、`field_defs`、`09-fields.js` | 字段 ID/类型/选项/条件、节点 ID/版本、五类适用路径；输出有效表单定义 |
| 权限策略 | `canSeeProject`、`designAllowed`、`prodAllowed`、`installAllowed`、报价过滤 | 基于人员、项目、节点和动作统一判定；返回前端可用动作，不只返回角色名 |
| 设计/生产/安装命令 | 各 `advance/save/rollback/resume` 路由 | 校验业务前提、计算变更、关联下游，不直接拼通知 HTTP |
| 出货与安装门禁 | `newApproval`、批次、ship 分支、`readyForInstallation` | 出货关联、审批轮次、真实发货、唯一安装及齐货判定 |
| 异常服务 | `syncProductionException`、`syncProjectException`、安装/批次异常 | 逐条登记、意见、阻塞调整、关闭；风险为投影，不覆盖阶段 |
| 数据保存 | `loadDB/saveDB`、`find/push` 与启动迁移 | 读写接口、事务、唯一约束、版本冲突、显式迁移和恢复 |
| 附件服务 | `upload/files`、节点历史扫描 | 文件归属、版本、敏感策略、下载和审计；不让浏览器直达私有目录 |
| 外部集成 | `feishu.js`、内嵌通知分支 | 身份、审批和通知适配；持久化待发送/已收事件，密钥留服务端 |
| 表单控制器 | `10-nodeform.js`＋CF 附加字段＋批次/出货手写表单 | 一个字段组件接口负责显示、取值、错误、草稿、回显；PC/手机同用 |

统一命令形态可以是：`保存节点资料`、`完成节点`、`退回节点`、`补正已发货资料`、`记录实际发货`，而不是开放“任意改某表 status”的接口。HTTP 路由仅解析请求和返回结果，业务服务负责授权与变更，存储层负责原子提交。

新提取模块先用清晰输入输出、JSDoc 类型或小范围 TypeScript 均可，不把全仓语言迁移列成前置任务。保留简单 Node 单体服务；不拆微服务、不引入分布式工作流。

### 9.2 数据结构：改需要改的，不把一切变成万能表

当前真实结构是 JSON 中的 `projects/design/production/batches/installations/aftersales/approvals/users/groups/files/logs/notifications/field_defs/config` 等集合，关联靠手动 ID。`designOf/prodOf/installOf` 用 `find()` 表达“唯一”，但没有存储约束。

建议保留这些业务实体含义，最小补足下列关系：

| 对象 | 需要补的结构 | 不要过度设计 |
| --- | --- | --- |
| 任务 | 稳定节点 ID、流程版本、记录版本；明确节点当前值与历史快照 | 不立刻改成所有实体共用一张万能任务表 |
| 人员分配 | 项目/任务与多人 ID 的明确关系；兼容主负责人展示 | 不按人名判断，不维护可互相矛盾的两份负责人 |
| 普通附加值 | 受类型验证的 `custom`；字段定义、稳定选项 ID、配置版本 | 不必每加普通字段就迁移数据库；也不必先建复杂 EAV 万能模型 |
| 查询与门禁字段 | 状态、归属、日期、关联等保留可索引的明确字段 | 不把所有状态与金额都埋入不受约束 JSON |
| 异常 | 独立问题记录及处理动作，关联来源任务/批次 | 不搞通用工单中心或绩效扣分系统 |
| 出货 | `shipments`＋`shipment_batches`，单批不拆数量 | 不扩展库存流水与成本核算 |
| 审批 | `approval_attempts` 关联一次出货，保存外部实例与轮次 | 不覆盖旧审批，不把驳回记录改成下一次申请 |
| 安装 | 按项目唯一，建档与可派工状态独立 | 不按每个生产批次创建安装任务 |
| 文件 | 元信息与归属/版本引用，私有物理存储 | 不在日志正文里推断文件属于谁 |
| 集成 | 小型 outbox/inbox，业务事务内写待发送事件 | 不急于 Kafka、复杂事件溯源或分布式事务 |

其中 `outbox` 是“业务已提交、等待发送的工作清单”；`inbox` 是“外部事件已接收和处理的凭证”。它们解决失败可重试和重复可识别，不承诺外部服务在网络故障下绝对只收到一次。重要动作仍需幂等键和回查。

### 9.3 数据库怎么选

**判断：正式多人业务不建议长期继续整库 JSON；但本轮不迁库，也不因为装过 PostgreSQL 就自动使用它。**

当前没有真实并发、部署和数据量测量。若仍是单台主机、一个服务进程、规模有限，优先评估 SQLite 的事务、约束、迁移与本地备份方式，运维最少；若明确需要多个服务实例、跨主机部署或持续较高并发写入，再选择 PostgreSQL。SQLite 同时只能有一个写事务，必须按实际负载验收，不能凭“公司人数不多”保证适用。参见官方[适用场景](https://www.sqlite.org/whentouse.html)与[事务保障](https://www.sqlite.org/transactional.html)。

关键不是先争论数据库品牌，而是让“项目＋下游任务＋历史＋通知待发记录”在一次业务提交中一致成功或一致失败，并用唯一约束防止重复创建。单独把 JSON 文件换成 SQL，但路由继续分散写多次，收益会很有限。

必须先明确业务主数据权威位置：推荐当前阶段先使本系统的业务状态可可靠保存，飞书作为身份/审批/通知边界；这是建议，不自动撤销用户早期“业务主数据放飞书”的设想。若仍要求飞书 Base 为主库，存储适配和跨表一致性方案需另行验证，不能套用本地数据库事务结论，更不能静默双写为双主。

### 9.4 自动化集中，但不要集中成另一个大文件

`转接生产已完成`、`实际发货已登记`、`异常已登记`等业务事件由明确命令产生；下游任务创建属于核心业务事务，通知则写待发送清单。

收件人按“当前负责销售、被分配生产负责人、采购岗位、审批岗位”求值，替换 `notifyByName`。同一业务动作拥有稳定事件键，重试不重复建任务；退回后重新完成需要新轮次，但不复制仍有效的下游任务。已完成审批只作事实保留，当前待办是否可继续单独判断。

### 9.5 PC、手机和 UI

保留当前公司名称、导航和绿色主色，不把工作系统做成展示型首页。最近截图显示主要问题是信息层次、空详情与动作位置，不是必须推翻视觉语言。

优先改：手机默认当前节点；资料按组折叠；节点点击只查看；底部清楚区分保存、提交及更多操作；退回在详情内二次确认；日期、人员、多选和文件共用组件；按钮状态来自服务端授权。电脑可保留列表与详情并排。

缩放按已确认员工设置处理，生产输入控件至少避免聚焦自动放大；不把强禁缩放当作解决布局溢出的办法，也不承诺绕过所有浏览器的无障碍缩放机制。

## 十、按什么顺序实施

**先做可验证的小步，不同时启动存储迁移、权限重写和 UI 翻新。以下是报告形成时的建议顺序；后续隔离实施状态以项目交付窗口沉淀和任务账本为准，不能把建议表当作已完成清单。**

| 步骤 | 具体工作 | 业务上马上得到什么 | 独立验收门槛 | 回滚/停止条件 |
| --- | --- | --- | --- | --- |

**重要：代码回滚和数据回滚不是一回事。** 新版本接受真实录入以后，恢复切换前备份会丢新数据。必须有维护窗口、写入冻结、变更日志和对账，或兼容旧版本读取的新结构；不能把“有 ZIP”称为可随时无损回滚。

## 十一、如何验证“更适合 AI 持续开发”

不是换成某个框架就适合 AI，而是每个改动都有明确范围和反证测试。

### 11.1 最小交接材料

继续使用现有项目交付沉淀和任务账本，不新增一堆同内容日志。恢复入口只需清楚指向：当前实际代码目录、试用/正式环境与数据边界、唯一业务母本、已确认规则 ID、各规则实现模块、测试命令、未决问题和最近验收证据。

一个业务纠正形成最小闭环：**决定日期＋业务说明＋实现文件＋测试场景＋当前发布状态**。必须区分“写入文档”“代码已改”“隔离通过”“用户验收”“正式生效”。

### 11.2 后续每次改动的固定检查

1. 明确它是普通信息字段、业务规则还是授权变化；确定影响的五类项目路径和当前在途版本。
2. 先补会失败的场景，再改最小模块；不顺带格式化或重写其他页面。
3. 业务计算使用纯函数测边界，接口用独立库测权限和事务，UI 测主要操作及四宽度。
4. 记录本次修改、保留的数据含义、回滚方法和未验范围；安全/数据迁移改动再做独立只读复核。
5. 发布后以请求、记录、关联和外部实例回读为证据，不只看页面提示成功。

原 `run-all-tests.sh` 会管理 8199 进程并调用 `clean-test-data.js`，后者读取原 `data/db.json` 后过滤记录写回，**本轮没有执行**。后续 AI 不应把它当普通无副作用测试。必须改成显式独立测试路径、拒绝真实目录，才能作为常规验收命令。

### 11.3 至少保留的回归场景

| 类别 | 必测场景 |
| --- | --- |
| 设计与字段 | 定制全设计路径；新增附加字段保存与必填；初量尺多人；仅最终报价限制；指定拆单人；其他四类适用路径 |
| 权限 | 同项目可见但不可编辑；多岗位组合不受顺序影响；演示外接负责人第二负责人；木工不能改油漆；字段接口不能绕过节点权限 |
| 退回 | 普通人员不能跨他岗交接；管理员重复退回；节点原值/文件/版本保留；未来/不适用节点拒绝；已发货仅补正 |
| 生产 | 日期空白、分批明确选择；并行外购在单批和多批；错误状态不能出货；源负责人多人继承 |
| 出货与安装 | 一批一次、两批合并一次、驳回再申请、重复提交；首批建一档、所有门禁满足才派工；安装意向后改是的补建 |
| 异常 | 两条问题独立存在；处理意见不等于关闭；仅管理层改非阻塞；阶段不被风险覆盖 |
| 文件 | 未授权列表/详情/历史/导出/下载拒绝；改标题不解除权限；替换保留版本；缺归属不放行 |
| 集成 | 真实审批拒绝、超时、重复及迟到事件、暂停后旧批准；远程实例存在但本地超时的对账 |
| 稳定性 | 错误提交无局部更新、两人同时提交、重启、中断写入、备份恢复、迁移回读 |
| 手机/PWA | 实体设备、日期/多选/文件、切账号、离线文本、断网后手动提交、填写时版本更新；不缓存完整敏感业务库 |

## 十二、现在最不应该做的事情

1. **不直接覆盖原系统为 system-v22。** 两版有不同数据目录、演示门禁、启动迁移和旧行为；先差异核对再按功能接续。
2. **不直接把 NocoBase 当正式底座。** 私有附件、业务归属权限、跨请求事务和维护收益仍有缺口。
3. **不同时重写前端、后端、数据库、流程和权限。** 发生回归时无法定位，也失去小步回滚能力。
4. **不把全部规则开放为配置。** 尤其审批通过、实际发货、管理员权限、历史保留、自动派工不得变成随便拖拽的条件。
5. **不只在前端隐藏按钮或字段。** 直接接口与附件 URL 才能检验权限底线。
6. **不把“按组有生产权限”当任意节点编辑权。** 木工、油漆、采购、发货的职责必须落到动作与记录上。
7. **不把普通回退当事务撤销。** 已发货、已完成审批等事实只能追加补正，不能删旧值装作没发生。
8. **不在启动时悄悄修历史状态。** 不认识的旧节点、旧异常阶段应停下核对，不强制归第一节点，也不补今天。
9. **不运行会清原数据的旧测试脚本。** 测试通过不能以清库为代价。
10. **不把本地审批结果冒充飞书结果。** 真实请求失败不能回退到模拟成功，填好 App ID 也不等于已集成。
11. **不建立本地库与飞书 Base 的无规则双主。** 先定每类事实的唯一写入权和同步边界。
12. **不把格式美化、换框架或 AI 大量生成代码当进度。** 优先看员工操作是否正确、一次改动是否少碰模块、失败是否可恢复。
13. **不删除 NocoBase POC 和已有业务成果。** 保留其验证结果，以后是否重评由用户决定。

## 十四、如何判断这次改造真的成功

| 用户目标 | 不是口号的验收标准 |
| --- | --- |
| 不丢已有成果 | S 已通过的业务回归保留；五类流程与现有历史数据有兼容对照；原系统保留 |
| 改字段少改地方 | 普通新增字段只操作字段设置；服务器/前端不再各写一份；保存、详情、退回都可见 |
| 改流程不伤其他流程 | 稳定节点 ID＋流程版本；五类路径契约测试；新旧在途有明确边界 |
| 权限不散落 | 所有写入口和文件入口引用同一策略；按钮状态由服务端授权结果产生 |
| 自动化不散落 | 业务命令产生事件；通知与外部审批由单独模块接收，持久化重试可查 |
| PC/手机共规则 | 同一个表单目录、接口、校验与授权，只改变布局；实体手机验收 |
| UI 能持续优化 | 业务命令不依赖 DOM；换页面层次不修改发货/退回规则 |
| AI/新会话能接手 | 一个恢复入口能找到当前版本、母本、模块、测试和未决项；不需要翻聊天猜状态 |
| 可测试可回滚 | 隔离路径强制；失败不局部落库；代码回退和数据回切分别演练 |
| 飞书解耦 | 模拟与真实适配共契约；业务服务不持有飞书密钥，不因接口失败伪造成功 |
| 长期维护且员工简单 | 新增常规字段不改代码；关键规则有明确模块；员工仅使用业务页面，不懂底层也能完成任务 |

**最终建议：选择 B，但只批准分阶段实施，不批准一次性大重写。先完成步骤 0～2 的安全与接续验收，再推进字段、存储及关键业务关系。** 这样既不放弃原系统，也不会因已经搭了 NocoBase 而被平台牵着走。
